# Custom 5-camera demo recording (left / right / top / bottom / front)

Your own fixed camera rig for saving demos, without touching any of the original
repo code. All five cameras sit on a sphere **in front of the table**, are fixed,
and look at the robot workspace, so each view covers the task well.

```
         top (60°)
         |
   left(-55°)--front(0°)--right(+55°)      <- on a sphere of radius 1.2 m,
         |                                   centered at the table workspace,
        bottom(-18°)                         looking at the robot arm
```

## Setup note (important)

The conda env created by `setup.sh` installs the *latest* mujoco, but this
robosuite fork still uses mujoco APIs (`MjData.qM`, the old `mj_fullM` signature)
that were removed in mujoco ≥ 3.2. The repo's own demo scripts crash on env
creation with:

```
AttributeError: 'MjData' object has no attribute 'qM'. Did you mean: 'M'?
```

Fix — pin mujoco to the version robosuite 1.5.1 supports:

```bash
conda activate know_your_camera
pip install mujoco==3.1.6
```

## Step 1 — Generate the 5 fixed camera poses

```bash
python gen_camera_poses.py --task liftrand --train_demos 50 --test_demos 10
```

- `train_cameras.json` / `test_cameras.json` — poses for the training/eval
  pipeline, in the same format as `policy_robosuite/camera_poses/*.json`
  (list of 4x4 cam-to-world matrices). The 5 fixed poses are repeated once per
  demo, so a training window `W(i) = [5i, 5i+5)` always contains the same rig.
- `custom_cameras.json` — the 5 named poses, used by the demo recorder below.

Check the views first (saves PNGs into `preview/`):

```bash
python gen_camera_poses.py --preview-only --task liftrand
```

Tune the rig without editing code, e.g.:

```bash
CAM_TOP_ELEV=65 CAM_BOTTOM_AZ=-30 CAM_RADIUS=1.4 python gen_camera_poses.py --preview-only
```

## Step 2 — Generate demos with images from the 5 cameras

```bash
python gen_demos_with_cameras.py --task liftrand --num_demos 50 \
    --poses_json camera_poses/custom_cameras.json --output_dir demos \
    --image_size 128
```

Trajectories are generated by the same motion-planning controllers as
`script_robosuite_demos/gen_robosuite_format_demo.py` (imported, not copied),
so the HDF5 layout is identical — plus per-timestep images:

- `obs/<camera>_image` and `next_obs/<camera>_image` — uint8 `[T, H, W, 3]`,
  gzip-compressed. `camera` ∈ {left, right, top, bottom, front}.
- `data.attrs['camera_names']`, `camera_poses` (4x4 cam-to-world per camera),
  `camera_intrinsics`, `camera_image_size` — recorded so the demos are
  self-describing.

Note on `next_obs` images: `next_obs[t]` is the state after action `t`, which is
the pre-action state of `t+1`, so `next_obs` images are the `obs` images shifted
by one frame (aligned with the other `next_obs` keys).

## Step 3 — Train with the fixed rig

Point the existing training code at the generated JSONs (copy them into
`policy_robosuite/camera_poses/` or pass `--camera_poses_dir`):

```bash
cd ../policy_robosuite
python train.py --dataset_dir ../custom_camera_demos/demos \
    --dataset_suffix eef_abs \
    --train_poses_file train_cameras.json --test_poses_file test_cameras.json \
    --camera_poses_dir ../custom_camera_demos/camera_poses \
    --m 5 --n 5 --num_side_cam 2 ...
```

Because the rig is fixed, every demo has the same 5 poses; with `--m 5 --n 5`
the window `[5i, 5i+5)` is exactly the rig, and `--num_side_cam 1|2` samples
one or two of the five views per training step. `eval.py` indexes poses by
episode directly, so any repetition count works there.

## Files

| File | Purpose |
|------|---------|
| `gen_camera_poses.py` | computes the fixed 5-camera rig, writes JSONs + previews |
| `gen_demos_with_cameras.py` | records demos with per-step images from the rig |
| `camera_poses/*.json` | generated pose files |
| `preview/*.png` | visual check of the 5 views |
| `demos/*.hdf5` | generated demos with images |
